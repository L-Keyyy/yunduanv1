# 云端衔接与缓存策略指引

本文档用于固定当前项目在“本地已完成、准备同步到 AWS、后续继续演进”阶段的判断口径。

后续讨论和实现时，默认以本文档为准，避免以下几类错误：
- 把“数据库查询”误当成“必须实时打 Ozon API”。
- 把“Seller 页面抓取”误当成“普通后端接口”。
- 把“缓存兜底”误删成“每次切页都重新抓取”。

## 1. 当前架构判断

项目当前有三类数据来源：

1. 本地/业务数据库
   - 订单、商品、库存、上传任务、定价模板、页面统计等。
   - 这类数据由系统自己保存，页面切换时直接查库即可。

2. Ozon 官方 API
   - 订单拉取、店铺校验、活动管理、通知、商品数量等。
   - 这类能力可以纯云端运行，不依赖浏览器页面。

3. Seller 页面抓取 + Chrome DevTools 9222
   - 仓库同步、Seller 类目趋势、热门标签/搜索词趋势等。
   - 这类能力依赖 Seller 登录态，不应当按普通 API 看待。

## 2. 云端职责边界

### 2.1 核心业务层

放在云端长期运行：
- FastAPI API
- 前端静态资源
- PostgreSQL
- Redis
- 定时任务 / Worker
- Ozon 官方 API 调用

### 2.2 浏览器协助层

保留为单独能力层，可以先与核心业务放在同一台 AWS，但逻辑上单独对待：
- Chrome 9222
- Seller 登录态
- 页面脚本执行
- Seller 页面数据抓取

原则：
- 浏览器协助层异常时，核心业务层不能一起失效。
- 浏览器抓取型页面允许回退缓存。
- 订单、商品、库存、活动等核心功能不能依赖 Seller 页面在线。

## 3. 总策略

总体采用：
- 数据库型页面：实时查库。
- Ozon API 型页面：实时查询或短缓存。
- Seller 抓取型页面：保留缓存，不做“每次切换都重新抓”。

同步策略采用：
- 定时同步为主。
- 手动同步为辅。
- 浏览器抓取型能力仍允许手动触发。

## 4. 功能矩阵

| 模块/页面 | 当前主要数据源 | 是否依赖 Chrome/Seller 页 | 页面切换是否实时查询 | 是否保留缓存 | 建议缓存/刷新策略 | 云端归属 |
| --- | --- | --- | --- | --- | --- | --- |
| 店铺管理 | 数据库 + 手动校验 Ozon API | 否 | 是，直接查库 | 不需要页面缓存 | 点“重验”时实时校验；可加 30-60 分钟后台校验 | 核心业务层 |
| 商品管理 | 数据库 + 手动商品同步 | 否 | 是，直接查库 | 不需要页面缓存 | 同步任务完成后刷新库；页面切换直接查库 | 核心业务层 |
| 库存管理 | 数据库 | 部分依赖。只有“同步 Ozon 仓库”依赖 Chrome | 是，直接查库 | 不需要页面缓存 | 仓库同步接口保留手动触发；库存列表直接查库 | 核心业务层 + 浏览器协助层 |
| 订单管理 | 数据库 + 手动/定时拉取 Ozon API | 否 | 是，直接查库 | 不需要页面缓存 | 订单同步定时跑；页面只读本地库 | 核心业务层 |
| 上传记录 | 数据库 + Ozon 任务状态刷新 | 否 | 是，直接查库 | 不需要页面缓存 | 点击刷新任务状态时调用 Ozon API | 核心业务层 |
| Dashboard | 数据库 + 少量 Ozon API | 否 | 是 | 可对少量 Ozon API 结果做短缓存 | 本地统计直接查库；商品总数类接口可短缓存 1-5 分钟 | 核心业务层 |
| 通知/消息 | 数据库 + Ozon API | 否 | 是 | 可选短缓存 | 前端 5 分钟轮询即可；多用户时可加 30-60 秒共享缓存 | 核心业务层 |
| 活动管理 actions/candidates/participating | Ozon API + 本地商品补充 | 否 | 是，但要做短缓存 | 需要 | 列表缓存 120 秒；商品详情缓存 600 秒 | 核心业务层 |
| 类目佣金 | 静态数据/整理数据 | 否 | 是 | 可不额外缓存 | 直接返回即可 | 核心业务层 |
| 定价计算器 | 本地计算 + 数据库模板 | 否 | 是 | 不需要 | 模板查库即可，计算实时执行 | 核心业务层 |
| Seller 类目趋势 | Seller 页面抓取 | 是 | 不建议每次切页都重新抓 | 必须保留 | 当前类目短缓存；失败回退磁盘/持久缓存 | 浏览器协助层 |
| Seller 全量类目浏览 | Seller 页面抓取 | 是 | 不建议每次切页都重新抓 | 必须保留 | 允许中频缓存；失败回退缓存 | 浏览器协助层 |
| 热门标签 / 搜索词趋势 | Seller 页面抓取 + 翻页采集 | 是 | 不建议每次切页都重新抓 | 必须保留 | 采集成本高，保留缓存和历史快照 | 浏览器协助层 |
| 同步 Ozon 仓库 | Seller 页面抓取 | 是 | 不适合自动随页面切换触发 | 必须保留结果 | 手动触发或低频定时，不随切页自动执行 | 浏览器协助层 |

## 5. 缓存保留结论

### 5.1 必须保留的缓存

- 活动模块短缓存
  - 候选商品和参与商品列表：保留。
  - 商品详情批量查询结果：保留。
  - 理由：活动页会频繁切换 action、翻页、补详情，不缓存会重复请求同一批产品信息。

- Seller 类目趋势缓存
  - 保留内存短缓存。
  - 保留持久化缓存/磁盘快照作为兜底。
  - 理由：抓取依赖 Seller 页面，失败时必须有回退结果。

- 热门标签缓存
  - 保留。
  - 保留历史快照。
  - 理由：该功能采集成本最高，包含翻页、动态趋势补齐、分组映射，不适合频繁重抓。

### 5.2 可以弱化或不需要的缓存

- 商品列表、库存列表、订单列表、店铺列表
  - 不需要额外页面缓存。
  - 直接查数据库即可。

- Dashboard 主体统计
  - 大多数项不需要缓存。
  - 只有实时 Ozon API 项可做短缓存。

- 通知
  - 当前单用户场景不需要复杂缓存。
  - 前端轮询即可。

## 6. 对“每次切换都查询一次”的判断

可以每次切换都查：
- 店铺列表
- 商品列表
- 库存列表
- 订单列表
- 上传记录
- Dashboard 本地统计
- 定价模板
- 类目佣金

不应当每次切换都重新查：
- Seller 类目趋势
- Seller 全量类目趋势
- 热门标签
- 同步 Ozon 仓库
- 任何依赖 Chrome 9222 和 Seller 登录态的抓取类功能

## 7. 缓存时长建议

以下是后续调整时的建议基线：

| 能力 | 建议时长 | 说明 |
| --- | --- | --- |
| 活动列表缓存 | 120 秒 | 当前实现合理，继续保留 |
| 活动商品详情缓存 | 600 秒 | 当前实现合理，继续保留 |
| Dashboard 中 Ozon 商品总数 | 1-5 分钟 | 避免频繁打 Ozon API |
| 通知共享缓存 | 30-60 秒 | 仅在多用户并发时考虑 |
| Seller 当前类目趋势 | 15-60 秒 | 短缓存，保证切页/切筛选不重复抓 |
| Seller 全量类目趋势 | 10-30 分钟 | 不宜日级，避免数据过旧 |
| 热门标签主缓存 | 10-30 分钟 | 不宜每次重抓，也不宜主缓存 24 小时 |
| 热门标签历史快照 | 1-7 天 | 作为趋势回放或失败兜底 |
| 仓库同步结果 | 30-60 分钟或手动刷新 | 取决于业务变动频率 |

说明：
- “短缓存”用于减少重复请求。
- “持久快照”用于抓取失败兜底。
- 两者不能混为一谈。

## 8. 后续实现时的固定规则

后续如果继续改代码，默认遵守下面的规则：

1. 不删除 Seller 抓取型功能的缓存兜底，除非同时提供等价的稳定数据源。
2. 不把“切换页面自动重抓 Seller 页面”作为默认策略。
3. 不给数据库型页面增加无必要的复杂缓存层。
4. 不把浏览器协助层和核心业务层耦合到“一挂全挂”。
5. 同步链路优先写成：
   - 定时同步更新数据库
   - 页面读取数据库
   - 必要时提供手动刷新按钮
6. 如果将来扩成多实例：
   - 短缓存迁移到 Redis
   - 持久快照迁移到 Redis / S3 / 数据库
   - 不继续依赖单机磁盘缓存作为唯一兜底

## 9. 一句话版本

后续统一按这句执行：

`凡是你自己的库，就实时查；凡是 Ozon 官方 API，就谨慎实时查；凡是 Seller 页面抓取，就一定要缓存。`
